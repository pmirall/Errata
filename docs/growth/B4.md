**The verifier, concretely.** Alphabet: 32 symbols, Crockford-style — `0-9` minus `0`/`1`, `A-Z` minus `I`,`L`,`O`,`U` — so nothing printed on paper is ambiguous and nothing is accented (a code must not need `core/utf8.h`'s crossing). 8 symbols × 5 bits = 40 bits. The image holds **fingerprints, not codes**: row *i* is `{ uint16_t fa; uint16_t fb; uint8_t item_id; uint8_t count; }` where `fa = crc16_ccitt(code_bytes||SALT_A)` and `fb = crc16_ccitt(code_bytes||SALT_B)`, both salts compile-time constants in `core/config.h`. Eight rows = 48 B of `.rodata`. `redeem_lookup()` computes both CRCs of what was typed and compares against the table.

## Riesgos
- **The obvious design is broken by CRC linearity, and it is the one a reasonable person reaches for first.** `code = payload || crc16(payload||SALT)` as a MAC is defeated by ONE published code: CRC-16 is linear over GF(2), so `crc(m ⊕ Δ) = crc(m) ⊕ crc(Δ) ⊕ crc(0)`, and a single known (payload, check) pair lets anyone mint a valid code for any other payload with pencil and paper. The design above avoids it by making the table a set of FINGERPRINTS of whole codes rather than a MAC over a varying payload — there is no algebraic relation between one row and the next. This has to be written into game/redeem.h or it will be 'simplified' back into the broken shape.
- **No offline scheme on this device resists an attacker holding the image, and the header must say so the way networking/creator_gate.h says it.** `esptool read_flash` yields the 32 B fingerprint table; finding a preimage of a 32-bit fingerprint in a 40-bit code space is ~2^32 CRC pairs — minutes on a laptop. What the scheme actually buys: `strings` on the image reveals nothing (the realistic attack), brute force at the panel is hopeless (2^32 against a thumb), and publishing one code does not yield the others. It buys deterrence and durability, not secrecy. Any comment implying otherwise is the defect.
- **The manual is printed identically for every unit, so a code is public the moment one buyer types it into a forum.** Device-binding (folding `device_id` into the fingerprint) would fix that and is a MANUFACTURING change — per-unit printing — not a firmware one. Say this out loud rather than letting someone discover it after the print run.
- **The salts freeze at the first print run, forever.** There is no v2 of a code printed on paper. This belongs in docs/decisions.md before the booklet goes to a printer, not after.
- **Inserting SCR_CODE mid-enum renumbers every id below it.** CLAUDE.md's note says FIVE guards fire and that the note used to say four; the fifth (`kRender[]`) was found by SCR_WIKI. All five are correct and all five must be attended to in one edit.
- **The reported globals delta is lumpy.** Comparable commits in this tree reported 0, +16, +112 and +128 for work of this size, because arduino-cli reports the DRAM segment total with alignment slack. Planning against the 26 B symbol sum and being handed +128 is how a 3,724 B margin gets surprised.
- **`docs/budget.md` §16 is stale by two features** (it says 1,354,812 / 59,468; the measured release build at this commit is 1,364,720 / 61,276). Anyone budgeting off it as written is 1,808 B optimistic on the scarce axis.
- **The manual already lies about the very screen this feature copies.** guide.typ:137-139 says *'Para el nombre, *A* recorre las letras y *B mantenido* pasa a la siguiente'*; the code has `GST_TAP_R` (B, a tap) stepping the letter and `GST_TAP_L` (A) moving the cell (screen_setup.cpp:211-217), and the booklet's own button table two pages later gets it right. A code screen written with the same grammar and documented by copying that paragraph inherits the error. This is exactly the class of defect CLAUDE.md's guide rule exists for and it is sitting in the booklet today.
- **The AJUSTES page of the booklet is already full and says so.** Its own source comment (guide.typ:1059-1073) records that P10-C9 had to delete a screenshot to buy room for one paragraph, and that the alternative was growing the booklet from 40 to 44 pages. A new row plus eight printed codes has to fit in existing slack or the honest report is 'this needs four more pages and here is what the other three should hold'.
