# RECON A3

## Lo que ya existe
FIVE item classes, not the seven the prompt's "7 classes" guessed at. `ItemKlass` is XP_CANDY, CAPTURE, CARE, BATTLE_MOD, EVOLUTION, generated from `balance.json ITEM_KLASS_ENUM` (Errata/src/data/items_table.h:57-64; tools/content/balance.json ITEM_KLASS_ENUM). The "7" in the prompt is `INVENTORY_SLOTS 7` — seven SLOTS, i.e. seven distinct KINDS carryable at once (Errata/src/persistence/save_schema.h:55, :362-374), which is unrelated to how many ids the table has. The pack ships 10 ids and the drop table 33 rows (Errata/src/data/items_table.h:112-123, :289-298 in encounter_table.h).

WHAT EACH CLASS DOES AT RUNTIME, and where it is consumed. One switch, `inv_use()` (Errata/src/game/inventory.cpp:199-243):
- XP_CANDY → `use_xp_candy()` (inventory.cpp:96-113) calls `xp_add(p, item_xp_value(id), XP_SRC_ITEM)`; `item_xp_value()` is value × ITEM_XP_CANDY_SCALE 8 (Errata/src/game/species.cpp:164-169; items_table.h:68). Returns IU_NO_EFFECT (not consumed) if neither level nor xp moved.
- CARE → `use_care()` (inventory.cpp:115-153): `value` is PERCENT OF A FULL BAR (`CARE_MILLI_PER_PCT`, inventory.h:116-119); `target` is a `CareTarget` (ALL or one of five, items_table.h:74-82), `param` is the PBS_* mask it also clears, with PBS_CORRUPTED routed through `cor_clear()` so the deadline dies with the bit (inventory.cpp:138-147).
- BATTLE_MOD → `use_battle_mod()` (inventory.cpp:155-168) writes the 4-byte `s_mod` static (inventory.cpp:14) and is taken ONCE by `inv_mod_take()`; applied in Errata/src/ui/screen_battle.cpp:814-825 and ONLY when `s_entry == BT_ENTRY_PRACTICE` — never on a linked battle and never on a DIAG battle, because BattleSetup is the replay input (inventory.h:60-75; screen_battle.cpp:798-813).
- CAPTURE → refused from the menu with IU_NOT_HERE and NOT consumed (inventory.cpp:231-236). It is spent by the encounter: `best_capture_item()` picks the highest-value CAPTURE row held (Errata/src/ui/screen_encounter.cpp:495-507), `cap_chance_permille()` adds value × ITEM_CAPTURE_SCALE 10 permille (Errata/src/game/capture.cpp:22-48; items_table.h:69), and `inv_remove()` spends it at screen_encounter.cpp:731.
- EVOLUTION → `use_evolution()` (inventory.cpp:170-197): it checks the bug's OWN rule is `EVOC_ITEM` with `cond_value == it.id` before asking `evolution_ready()`, and does not spend the key otherwise.

THE BAG UI is a MODE of SCR_CARE, not a ScreenId (Errata/src/ui/screen_care.h:38-48). `care_bag_rows()`/`bag_item_at()` walk the ITEM TABLE in id order 1..ITEM_COUNT, not the slot array (screen_care.cpp:86-107), so rows never reshuffle. `bag_render()` (screen_care.cpp:152-176) draws "NAME xN" — NO per-item icon, despite gen_content's banner claiming one (tools/gen_content.py:438). `bag_use()` (screen_care.cpp:209-232) maps ItemEffect to one of seven toasts through `item_reaction()` (screen_care.cpp:199-207).

HOW ITEMS ARE AWARDED: only the ITEM encounter outcome. `encounter_roll()` calls `item_pick_drop(category, rarity_min, rarity_max, roll)` and falls back to ENC_OUT_NOTHING if it returns 0 (Errata/src/game/encounters.cpp:240-246). `item_pick_drop()` is a two-stage pick — weight-pick inside the network category, then REJECT anything outside the encounter row's rarity band (Errata/src/game/species.cpp:132-161). The pool is `balance.json ITEM_DROPS` → `ITEM_DROP_TABLE[]`, 33 rows, per-category weights summing to exactly 100 (encounter_table.h:123-156). The screen adds it to the bag on ENTRY, not on a keypress, and toasts STR_ENC_BAG_FULL when `inv_add` returns 0 (screen_encounter.cpp:531-541). Nothing else awards items; `DIAG give_item` is dev-only (Errata/src/dev/diag_core.cpp:352-377). Measured: NOTHING an item does changes encounter probability — `encounters.cpp` reads no inventory at all.

SCHEMA: NO BUMP NEEDED to append ids. `InvSlot{item_id,count}` is 2 B and `Inventory` is 32 B with zero padding and zero reserved bytes (save_schema.h:356-375). The persisted thing is the ID, and ids are positional (`it.id == index + 1`, items_table.h:130). So APPENDING ids 11..N is free; INSERTING or renumbering silently rewrites every saved bag and must never happen. Nothing in the load path validates item ids (`save_manager.cpp:922-924` restores the blob verbatim; `validate.cpp` has no item rule), and an id above ITEM_COUNT is simply invisible because every consumer loops 1..ITEM_COUNT (screen_care.cpp:89,101; screen_encounter.cpp:499; diag_core.cpp:358).

DEAD VOCABULARY THE PACK NEVER USES — this is where "more items inside the existing classes" has real content to add: of six CareTarget values only ALL and HEALTH ship; of three BattleStat values only ATK and DEF ship (items_table.h:112-123). `ITEM_BSTAT_SPD`, `CARE_TGT_HUNGER`, `CARE_TGT_HAPPINESS`, `CARE_TGT_CLEANLINESS`, `CARE_TGT_ENERGY` are emitted, asserted and reachable by `use_care()`/`use_battle_mod()` and named by no shipped row.

CONTENT_VERSION is a hash of the JSON and WILL move (Errata/src/data/content_version.h:30; gen_content.py:536-580). It is stamped into saves but never compared on load (save_manager.cpp:204,496 write it; no reader rejects). It IS compared on the wire — `battle_init`/`setup` reject a peer at a different CONTENT_VERSION (Errata/src/game/battle.cpp:347, :1032). That is correct behaviour, not a blocker.

## Riesgos
- THE REBALANCE IS THE ONLY FIDDLY PART AND IT IS POLICED TWICE. Each category's ITEM_DROPS must still sum to exactly 100 (constexpr static_assert at encounter_table.h:397) and the empirical distribution must still match the weights to +/-(10%+6) over ~600 item events per category (test_encounters.cpp:636-640). Adding weight to a category without taking it from somewhere fails the first; taking it from the wrong row can fail the second.
- AN ITEM WITH THE WRONG RARITY FOR ITS CATEGORY IS SILENTLY UNGETTABLE. PUBLIC/HOME/UNKNOWN ITEM rows band 0..1, so a rarity-2 item listed only there is picked never. `item_pick_drop()` rejects it after the weight pick (species.cpp:145-149) and `encounter_roll()` converts the empty pick to ENC_OUT_NOTHING (encounters.cpp:246). Nothing in the tree catches this today - it is exactly what the new obtainability test is for.
- DO NOT ADD AN EVOLUTION ITEM. verify.py:344 requires every EVOLUTION item to be the cond_value of a real cond=ITEM evolution rule; test_content.cpp:673-695 pins keys==1 and id==9 and EVOC_ITEM rules==1; and EVOLUTION_RULES_COUNT is asserted == SPECIES_FAMILY_COUNT * 2 == 40 (test_content.cpp:737-739), so a new rule cannot simply be appended - an existing family's rule would have to be re-pointed. That is a roster change, not an item change.
- DO NOT SHIP A CARE ITEM WHOSE `clears` NAMES ASLEEP OR FAINTED. PBS_ASLEEP is RE-DERIVED from the daylight sim at the end of every mutator - status_sync() rebuilds status from view.flags (sim.cpp:233-244) - so an item that clears it is undone on the next tick. Nothing in src/ ever SETS PBS_FAINTED (grep: only battle.cpp:333 and validate.cpp:254 read it; screen_battle.cpp:283 clears it), so a 'revive' item would clear a bit nobody sets. Both would be items that pass every gate and do nothing - the exact defect P5-C4 spent a whole chunk removing from item 9.
- A PRE-EXISTING HAZARD THE SAME MECHANISM CREATES FOR PBS_SICK, worth knowing before adding a second SICK-clearing item: use_care() writes BugInstance.status directly (inventory.cpp:141-146) while the sim's working copy view.flags is only loaded from status at sim_bind() (sim.cpp:1234). status_sync() then rewrites status from view.flags. If the sim is bound to the same Bug and PF_SICK is still set, the clear can be undone. This is not A3's to fix, but a new SICK-clearing item multiplies it, and a test that uses an item and then ticks the sim would settle it either way.
- ITEM_COUNT HAS A HARD CEILING OF 15 TODAY. tests/test_encounters.cpp:574-577 tallies into a fixed uint32_t seen[16] guarded by CHECK(ITEM_COUNT < 16). The CHECK is honest, but it means item 16 turns a green suite red rather than a stack smash - fix the sizing in this commit or the next growth item pays for it.
- IDS ARE PERSISTED AND POSITIONAL. `it.id == index + 1` (items_table.h:130) and InvSlot.item_id is a saved byte (save_schema.h:356-360). Inserting an id in the middle, or reordering items.json, rewrites the meaning of every bag on every device with no gate and no migration - the load path does not validate item ids at all. APPEND ONLY.
- THE MANUAL IS ALREADY LYING ABOUT AN ITEM AND WILL LIE ABOUT FIVE MORE. docs/manual/content/guide.typ:345-363 is a by-name table no gate reads, and :352 already describes Cebo as making encounters likelier when it is ITEM_KLASS_CAPTURE and encounters.cpp reads no inventory. It is also a typeset A6 booklet whose page count must stay a multiple of 4 (tools/build_manual.sh:111) - five more table rows can push a page. This is the guide agent's job and it is why CLAUDE.md makes it a blocking step.
- CONTENT_VERSION moves, so two devices on different builds refuse to battle (battle.cpp:347, :1032). Correct and intended; mention it in the commit message so nobody reports it as a regression.
- BATTLE_MOD ITEMS ONLY WORK IN THE PRACTICE BATTLE (screen_battle.cpp:814). A third BATTLE_MOD is a third item whose effect is invisible in a linked fight - which is defensible and documented (inventory.h:60-75), but the manual and the web must say so or the player will think the item is broken.
